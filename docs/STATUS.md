## 驗證結果

### 排程考慮額度（2026-11-25，分支 `quota-aware-scheduling`）

- **問題**：排程和議題標籤開的任務不管額度剩多少都會立刻開始，可能把訂閱額度用到見底，你自己要用時反而沒了。另外 Joy 只在 single 模式記下 provider 的額度回報，review loop 等其他 run 的回報被丟掉，交接判斷也看不到。
- **做法**：所有 agent run 的事件都經過 `trackUsage`（用量統計＋額度狀態），額度狀態多記每個時間窗的最高使用率。`startTask` 多一個 `unattended` 參數，只有排程與議題標籤輪詢會帶（助理的「do #12」是你在要求，不算）。任務要用的 provider 中有一個額度回報仍有效（還沒到重置時間；沒給重置時間的算一小時）且已用完或使用率 ≥ `fallback.defer_unattended_at`（0.5–1，預設 0.9），任務就維持 `queued`、記 `quota.deferred`（provider、使用率、開始時間），在重置時間（加 `quotaResumeBufferMs`）重新判斷，沒有更新的高用量回報就從頭開始（不是 resume）。重開 Joy 時依事件裡的時間重新排程。排程的對話訊息會說任務在等額度。網頁時間軸顯示「額度快用完（claude-cli 已用 93%）：等到 … 再開始」。
- **測試**：server（自己的任務回報 95% 後照常完成、排程的任務被延後並記下 provider／使用率／時間、重置後從頭開始；review loop 的審查者回報額度用完後 `/api/quota` 顯示 limited）；config（預設與範圍）；web `policy-events.test.ts`。根目錄 `pnpm check` 通過（1673 tests）。
- **沒驗證到**：真實 Claude／Codex 的使用率回報格式只靠既有 fixture；重開 Joy 後延後任務的接續沒有整合測試（沿用 `quota.queued` 的同一套排程）。

### 變更面板隱藏 git 檔頭（2026-11-25，分支 `hide-diff-headers`）

- **做法**：`planDiff` 用 `withoutFileHeader` 去掉每個檔案第一個 hunk 之前的 git 檔頭；hunk 裡以 `---`／`+++` 開頭的程式碼不受影響。檔頭之外的行（模式變更、二進位檔）保留，因為沒有別的地方會顯示。檔名列多了「新檔案」／「已刪除」，取代原本的 `new file mode`／`deleted file mode`。只改網頁。
- **測試**：`diff.test.ts`（改名檔頭、hunk 裡像檔頭的程式碼、模式變更、二進位檔）；e2e `task-diff-allow.spec.ts`（第一行是 `@@`、沒有 `diff --git` 與 `+++`、行數與分頁跟著少 3 行）。整套 e2e 145 個通過；根目錄 `pnpm check` 通過（1670 tests）。
- **沒驗證到**：沒有截圖（fake-preview 沒有任務），只靠 e2e 確認畫面。

### 各角色 token 統計（2026-11-25，分支 `role-token-stats`）

- **問題**：任務頁已經有該任務各角色的用量，但全域只有 `usage` 表（provider × 天），看不出 token 花在實作、審查還是助理與背景工作，也看不出輕量審查省了多少。
- **做法**：migration 30 新表 `role_usage`（role × provider × model × 天，STRICT，role 有 CHECK：`implementer`、`reviewer`、`judge`、`assistant`、`background`、`safety_review`、`peer`；計數不能為負）。不回填，舊用量沒有角色可歸。server 的 `persistUsageEvent` 改成帶角色與 model，同時寫 `usage`（預算、額度照舊）與 `role_usage`；十個呼叫點各自標好角色。`GET /api/stats` 沒選專案時多回 `roles`（依期間加總、依角色再依 token 排序）與 `rolesSince`。網頁統計頁最上面的「用量分布」表：工作、模型、占比、輸入（含快取）、輸出、費用。
- **測試**：db `role-usage.test.ts`（加總與排序、期間含頭尾、只收計數與已知角色）；server（review loop 任務的實作與審查各自記到對的模型、期間外為空、選專案時不回）；web `usage.test.ts`（解析、占比）；e2e `stats.spec.ts`（表格內容、快取、起始日、選專案後消失）。fake-preview 看過空狀態。根目錄 `pnpm check` 通過（1668 tests）。
- **沒驗證到**：真實 CLI 回報的 token 量；助理與背景工作的記錄只靠呼叫點標註，沒有個別的整合測試。

### 審查強度依變更大小調整（2026-11-25，分支 `adaptive-review`）

- **問題**：不管改一行還是改三百行，審查者都用同一個 effort（預設 Codex `gpt-6.1-sol` medium），小改動的審查大多是在花 token。
- **做法**：`packages/orchestrator` 的 `isSmallChange`：加減行數合計不超過門檻，或每個檔案（改名的話新舊路徑都算）都是 `.md`／`.mdx`／`.markdown`／`.txt`／`.rst`／`.adoc`，就算小改動；空 diff 不算。`ReviewLoopInput.smallChangeReviewer` 有設時，小改動的那一輪審查改用它，`phase` 事件記下實際用的 model。每輪都依整份 diff 重新判斷。server 的 `smallChangeReviewer`（`review-strength.ts`）只換 effort、不換 provider 或模型，所以審查紀錄、usage 歸屬、跨模型檢查都不受影響；設定的 effort 不比原本低，或那個模型不支援該 effort 時就不用。比賽的合併審查不套用。不跳過審查。
- **測試**：orchestrator（第 1 輪小改動用輕量審查、第 2 輪變大回到原本的審查者；行數、只改文件、改名、空 diff）；server `review-strength.test.ts`（預設、關閉、不會更輕、模型不支援）與 `server.test.ts`（預設 low、`small_change_max_lines: 0` 時維持 medium）；config（預設值與驗證）。`composer-switch.test.ts` 關掉這個設定，因為它驗的是換手後審查者設定被保留。根目錄 `pnpm check` 通過（1662 tests）。
- **沒驗證到**：真實模型用 low effort 審小改動時，漏看的比例與省下的 token。

### 審查第 2 輪起只看改過的部分（2026-11-24，分支 `review-followup-rounds`）

- **問題**：每輪審查都是全新 run（ephemeral），重送整份 diff（上限 6 萬字元），也不知道自己上一輪說過什麼，容易重讀已通過的檔案、每輪挑新的小毛病而拖長輪數。
- **做法**（只動 `packages/orchestrator`，`core` 沒動）：review loop 記下上一輪的審查結果、diff 和實作者修完後的回覆。下一輪的 `reviewPrompt` 帶 `PreviousReview`：列出上一輪摘要與 findings、實作者回覆，要求先確認每個 blocker／major 是否解決，新問題只針對改過的程式（blocker 例外）。diff 依檔案切開比對（`splitPatch`、`patchSinceLastReview`）：只送內容有變或新加入的檔案，沒變的列檔名（審查者可自己讀），改回去的檔案另外列出。上一輪是「審查通過但檢查失敗」時，提示文字也照實說。第一輪與接續任務的第一輪不變。
- **測試**：`review-loop.test.ts`（第 2 輪 prompt 有上一輪 findings、回覆、改過與新增的檔案，沒改的只列名，移除的另列）；`prompts.test.ts`（切檔、結尾換行不影響比對、沒有任何變動、長 diff 上限、通過但檢查失敗的說法）。`pnpm test` 1646 通過。
- **沒驗證到**：真實模型的審查輪數與 token 是否真的下降。

### Diff 逐行留言（2026-11-23，分支 `diff-line-comments`）

- **做法**：`numberDiffLines` 依 hunk 標頭算新舊行號（行號用 `data-line` 加 CSS 顯示，不進行的文字）；新增與未變的行留言指向新檔行號，刪除的行指向舊檔。留言像草稿一樣存在 localStorage（`joy.diffComments.<taskId>`）。「送出留言」用 `diffCommentsMessage` 整理成一則訊息（檔案、行號、引用該行、意見），走 `POST /api/tasks/:id/messages`，任務在跑時排隊，跟輸入框一樣。比賽任務與工作副本已移除的任務沒有留言按鈕。server 沒改。
- **測試**：`diff-comments.test.ts`（行號、留言目標、訊息格式與排序、localStorage 驗證）；e2e `diff-comments.spec.ts`（行號、新增／刪除行留言、Esc 取消、⌘Enter 存、重新整理後還在、刪除、送出內容、無法接續的任務沒有按鈕）；fake-preview 實際走過一次（送出後任務跑第 2 輪）。
- **沒驗證到**：真實 agent 收到留言後的處理品質。
